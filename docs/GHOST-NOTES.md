# Ghost — hard-won platform knowledge

**Probed:** 2026-07-28, against the probed Ghost install (Ghost **6.44**). A follow-up
probe on 2026-07-29, same site, corrected the `healthCheck` endpoint (see the
`/site/` row below). A third on 2026-08-03, same site, measured scheduling and
backdating (the `status: "scheduled"` rows).
**Auth:** Custom Integration Admin API key (Ghost Admin → Settings → Integrations).

This file exists for the same reason `docs/WORDPRESS-NOTES.md` does: every line below
is traceable to a real request made against a real Ghost install during this probe,
not to documentation or memory. Four separate defects reached production because a
mocked test agreed with an assumption about Ghost's behaviour; each was caught only
by a single real API call. Do not widen anything here without another probe that
proves the change — see `src/plugins/platforms/ghost/html-profile.ts`, which encodes
these behaviours as data and carries the same warning.

## Behaviour → consequence

| Behaviour | Consequence |
|---|---|
| The Admin API key is `id:secret`. The `secret` half is **hex** and must be decoded to raw bytes before signing — signing the hex *string* produces a token Ghost rejects with a bare 401. | `ghostToken` (`src/plugins/platforms/ghost/auth.ts`) splits on `:` and decodes `secret` with `Buffer.from(secret, 'hex')` before HMAC-signing. A key with a non-hex secret (e.g. a pasted Content API key, which is shaped differently) is rejected before ever reaching the network, with a hint pointing at the mixup. |
| Auth is a per-request, short-lived **HS256 JWT**: header `{ alg: 'HS256', typ: 'JWT', kid: id }`, payload `{ iat, exp: iat + 300, aud: '/admin/' }`, sent as `Authorization: Ghost <jwt>` plus `Accept-Version: v6.0`. A bearer-token attempt returns 401 with no useful body. | Every request signs a fresh token (`ghostToken`) rather than reusing one — a 300-second expiry makes a long-lived token useless anyway. `health_check` sends a real signed request rather than merely checking that a key string is present, since a malformed key still "looks" present. |
| The Admin API base is `{site.url}/ghost/api/admin/` **by default**, but two of three real sites in this project actually served it on a different host/path than the public site. | `api_url` in `sites.yaml` overrides the derived endpoint; a 404 on `/site/` with an otherwise-valid key is the signature of this mismatch, not a bad credential. |
| Image upload is `POST /images/upload/`, **multipart**, field `file` plus `purpose=image`. The uploaded part must carry an explicit MIME type — without one the part is sent as `application/octet-stream` and Ghost rejects it with **415** "Please select a valid image." Response shape is `{ images: [{ url }] }`, with no documented `id`. | `mimeFor()` maps the file extension to a MIME type before every upload. `uploadImage` reads an `id` defensively in case a future/self-hosted Ghost version returns one, but never assumes it — Ghost's own `createPost`/`updatePost` only ever take `feature_image` as a URL, so nothing on this platform needs the id the way WordPress needs `featured_media`. |
| Post creation is `POST /posts/?source=html` — **the `source=html` query parameter is required**; omit it and Ghost expects Lexical JSON instead and silently drops the HTML body. Payload is `{ posts: [ { ... } ] }`. Verified: 201, HTML round-trips intact, `lexical` stays null. | Every `createPost` call includes `?source=html`. This is the single most consequential parameter in the adapter — its absence doesn't error, it silently discards the entire post body. |
| Post update is `PUT /posts/{id}/?source=html` and **requires the post's current `updated_at`** in the payload (optimistic-concurrency check). | `updatePost` first `GET`s the post for its `updated_at`, then includes it in the `PUT` body — omitting it causes Ghost to reject the update. |
| `GET /users/me/` returns **404** for an API integration — an integration is not a "user" in Ghost's model. | `listAuthors` uses `GET /users/?limit=all` instead of a users endpoint that 404s unconditionally for this auth type. |
| **`GET /site/` requires no authentication at all.** Probed 2026-07-29 against the probed Ghost install: a fabricated-but-well-formed key (`'0'.repeat(24) + ':' + 'a'.repeat(64)`) got a **200** back with the real site title and version, identical to the response for the genuine key. `healthCheck` used to call `/site/` and treat that 200 as proof the key worked — it was not; it proved nothing about the key. `GET /config/` (also probed the same day, same two keys) genuinely requires the signed JWT: the real key gets **200** with `{ config: { version, ... } }`, the fabricated key gets a real **401** `{ "errors": [{ "code": "UNKNOWN_ADMIN_API_KEY", "message": "Unknown Admin API Key" }] }`. `/users/`, `/tags/`, and `/roles/` all showed the same 200-vs-401 split; `/config/` was picked as the smallest response body. | `healthCheck` (`src/plugins/platforms/ghost/index.ts`) now probes `GET /config/` first — a 401 there means `ok: false` and the request stops. Only once that call has already succeeded does it make a second, best-effort call to the still-unauthenticated `GET /site/` purely to recover the friendly site title for the success `detail` string; that second call can never turn a bad key into `ok: true`. |
| Ghost silently ignores unknown or read-only fields on write rather than erroring — sending `excerpt` (read-only; the writable field is `custom_excerpt`) returned **201 with the value discarded**, no error, no warning from Ghost itself. | `droppedFields()` (`src/plugins/platforms/ghost/index.ts`) compares every field the caller sent against what Ghost's own response echoes back, and returns a warning naming any field that came back null/undefined/empty — the mechanism that also makes `schema_injected` honest for `codeinjection_head` (see `post-tools.ts`). |
| `target="_blank"` is **stripped** on ingest: submitted `<a href="…" target="_blank" rel="noopener noreferrer">` is stored as `<a href="…" rel="noopener noreferrer">`. `rel="noopener noreferrer"` **does** survive. | `keepsLinkTarget: false` in `GHOST_HTML_PROFILE`. `score_draft` must not require `target`, and the writing brief must not ask for it — requiring an attribute the platform silently discards trains the writer to produce noise. `rel="noopener noreferrer"` is still worth requiring. |
| Heading `id` attributes are **generated automatically** by Ghost — `<h2>Probe heading</h2>` is stored as `<h2 id="probe-heading">` regardless of what (if anything) was hand-written. | `generatesHeadingIds: true`. The brief must not hand-write heading ids; doing so is wasted effort since Ghost overwrites them anyway. |
| A defined set of tags survive ingest **with their styling intact**: `p h2 h3 h4 strong em blockquote ul ol li a table thead tbody tr th td figure figcaption img hr code`. | `GHOST_HTML_PROFILE.preserved`. This is the safe tag list for anything that needs to keep inline styling. |
| A separate set is **unwrapped** on ingest: `div section aside span small pre mark dl dt dd header footer article main nav`. The inner *text* survives; the element and every style, border, and background are discarded. This is **worse than an error** — the post still publishes, just silently stripped of the visual structure the writer intended. | `GHOST_HTML_PROFILE.unwrapped`. A `<div>`-based card silently becomes bare text. The writing brief must steer writers away from `<div>` cards entirely, not merely warn that styling might not survive. |
| Inline `style=` attributes survive on `preserved` elements; `class=` attributes do **not** survive anywhere. | `inlineStyles: true`, `classAttributes: false`. Any visual design must be inline-styled, never class-based — "No `<style>` blocks. Inline styles only." / "No class attributes." are both in `GHOST_HTML_PROFILE.notes`. |
| A **standalone** `<blockquote>` is a native Ghost node: the converter **rebuilds** it, discarding the inline style and any inner `<p>` entirely. A bare `<blockquote style="...">` came back as plain `<blockquote>`. | `blockquote: 'native-rebuilt'`. Unlike WordPress (`passthrough`), a styled blockquote on Ghost loses its styling — it remains usable as an *unstyled* summary container (see next row) but never as a custom-styled one. |
| **A `<figure><img>` is REBUILT as a native Ghost image card.** Probed 2026-07-30 by read-back: submitted `<figure style="margin:32px 0;"><img src="…" alt="…" style="width:100%;height:auto;border-radius:12px;display:block;"><figcaption style="…">…</figcaption></figure>` came back as `<figure class="kg-card kg-image-card kg-card-hascaption"><img src="…" class="kg-image" alt="…">`. Every inline style was discarded and Ghost's own card classes were applied — the same converter behaviour as a standalone `<blockquote>`, not the attribute-level filtering that happens elsewhere. The `src` and `alt` survive. | The writing brief still instructs the styled figure, because WordPress needs `width:100%;height:auto` to stop an image overflowing the content column and Ghost discards it harmlessly. The brief says so explicitly rather than claiming the styles render on both. Do not "fix" a Ghost image by adding more inline style — the converter will drop it. |
| **Scheduling** (probed 2026-08-03): a scheduled post is `status: "scheduled"` plus `published_at` as ISO-8601 (`Z` or an explicit offset — both accepted). `status: "scheduled"` with **no** `published_at` is a **422**, `context: "Value in published_at cannot be blank."` Sub-second precision is truncated on write (`…:51.364Z` stored as `…:51.000Z`). | `toGhostPost` renames Byline's `publish_at` to Ghost's `published_at` — explicitly, because that loop copies unrecognised keys verbatim and the field used to reach Ghost by coincidence rather than by decision. `toWholeSecondIso` truncates before sending so the read-back comparison can be an exact equality. |
| A past `published_at` on a scheduled post is **rejected, not silently published**: 422, `context: "Date must be at least -2 minutes in the future."` Measured boundary: `now-110s` accepted, `now-125s` refused — the floor really is two minutes back. There is no minimum *forward* lead; `now+10s` was accepted. | The opposite of WordPress, which silently publishes instead of erroring. `MIN_SCHEDULE_LEAD_MS` (2 min) in `schedule.ts` is set by WordPress's requirement, not this one — a floor that satisfies WordPress satisfies Ghost automatically. |
| **`status: "published"` with a FUTURE `published_at` publishes the post immediately and stores the future date anyway** — 201, live URL, no error. WordPress converts the same request into a scheduled post. | The single worst cross-platform divergence in this codebase: one request, two opposite outcomes, neither platform reporting a problem. `resolveTiming` refuses the combination (`SCHEDULE_STATUS_MISMATCH`) rather than forwarding an input that means two different things. |
| **Backdating** works on create and update: `status: "published"` with a past `published_at` stores the date exactly, to the second, arbitrarily far back (3 years probed). `draft` → `scheduled` and `scheduled` → `draft` both work via `PUT`; unscheduling **retains** the stored `published_at`. **`published` → `scheduled` is a 422**: `"Your post is already published, please reload your page."` | Backdating and unscheduling need no special casing. `update_post`'s description names the already-published refusal and tells the caller to go via `draft`, since Ghost's own message does not suggest it. |
| **The blog's timezone** is at `GET /settings/`, which returns a flat array of `{ key, value }` pairs (113 of them on the probed install). The `timezone` key holds an **IANA zone name** — `"Asia/Kolkata"` on one probed blog, `"Asia/Dubai"` on another — never a numeric offset. | `GhostAdapter.siteTimezone()` reads that key, and `schedule.ts` resolves a wall-clock `publish_at` against it. An IANA name is what makes daylight saving resolvable per instant; a numeric offset would be wrong for half the year in any zone that observes it. |
| On a 422 the useful reason is in `errors[0].context`; `errors[0].message` is the generic `"Validation error, cannot save post."` | The adapter surfaces `context` as the `ToolError` hint. Without it a caller gets a validation failure that names no field — both scheduling refusals above are invisible in `message`. |
| A styled `<table>` is the **only** container that survives ingest with its styling completely intact. A `<blockquote>` survives as an element (per the row above) but loses its styling. | `visualContainers: ['table', 'blockquote']` — `table` is listed first and is what writers are told to use for any visual block; `blockquote` remains an acceptable, if unstyled, fallback. |

## The one trap, verbatim

**`POST /posts/` without `?source=html` does not error — it silently drops the body.**

Ghost's Admin API defaults to expecting Lexical JSON for post content. Send plain
HTML without the `source=html` query parameter and Ghost accepts the request (201),
creates the post, and simply has no HTML in it — `lexical` stays `null` and there is
no error surfaced anywhere naming the mistake. Every `createPost`/`updatePost` call in
`src/plugins/platforms/ghost/index.ts` includes `?source=html` for exactly this
reason — it is the single most consequential query parameter in the adapter.

## Where this lives in code

- `src/plugins/platforms/ghost/auth.ts` — JWT signing.
- `src/plugins/platforms/ghost/index.ts` — the adapter: requests, `droppedFields`,
  upload, tags, authors.
- `src/plugins/platforms/ghost/html-profile.ts` — `GHOST_HTML_PROFILE`, the behaviours
  in this file's table encoded as the `HtmlProfile` shared by `score_draft` and
  `build_writing_brief`.

Unlike WordPress's, Ghost's HTML ingest behaviour does not vary by account or
install — `GHOST_HTML_PROFILE` is a constant, not resolved per site.
